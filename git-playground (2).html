01 What is version control?

The problem it solves

Version Control Systems (VCS) track changes to files over time. They let you recall any earlier version, and they let a team work on the same project without overwriting each other's work.

Software teams change code constantly. One developer builds a new feature while another fixes an unrelated bug, and each touches several files across the project's folder tree. Their changes can clash. Any change can also introduce a new bug, so testing and development run side by side until a new version is ready. Version control records every individual change by every contributor, and surfaces conflicts in an orderly way without blocking the rest of the team.

02 Two architectures

Centralized vs distributed version control

In a centralized system (CVCS) there is one repository on one server. Each developer checks out files, and every commit goes straight to that server. In a distributed system (DVCS) every developer holds a full copy of the repository, history included. You commit locally, then push to and pull from a shared server when you choose. Git is distributed.

03 Tool vs service

Git and GitHub are different things

The tool

Git

An open-source distributed version control system. It runs on your own computer, handles projects from tiny to very large with speed, and coordinates work among developers.

Works with no internet and no account. You use it from the command line or an editor.

The service

GitHub

A company that hosts Git repositories in the cloud. Its web interface makes Git easier for individuals and teams, adds pull requests and code review, and lets anyone host public repositories for free.

It earns money from private repositories and business plans for managing teams and security. GitLab and Bitbucket offer similar services.

A useful comparison. Git is like email itself; GitHub is like Gmail, one popular place to keep and share it. You can use Git without GitHub, but not GitHub without Git.
04 The Git lifecycle

The three states, hands-on

Every file in a Git project lives in one of three places. Learn these and most Git commands become obvious.

  • Working directory, the workbench. Where you edit files.
  • Staging area, the shopping cart. You pick which changes go in the next snapshot with git add.
  • Repository (.git), the photo album. git commit -m "msg" saves the staged snapshot permanently.

A fourth place, the remote, is a copy on a server such as GitHub. git push sends your commits there.

How to try every command from section 05 (Scenario B)
  1. Choose Scenario B. The Remote column shows the team's project on GitHub, and your folder is empty.
  2. git clone https://github.com/team/my-site.git copies every commit and file to your laptop and sets up origin for you.
  3. git config user.name "Your Name" and git config user.email "you@example.com" set who you are.
  4. Click edit on index.html (or type edit index.html), then git add index.html.
  5. git commit -m "Update heading" saves it in your local repository. It is marked not pushed.
  6. git push origin main sends your commit to the Remote column.
  7. Click Simulate: a teammate pushes a commit. This is Developer B. Run git status: it still says up to date, because you have not asked the remote yet.
  8. git fetch downloads the commit, but your files stay the same. git status now says you are behind. Then run git merge origin/main to bring the commit in.
  9. Click the teammate button again, then git pull origin main. That is fetch and merge in one step.

Bonus: make your own commit, let the teammate push, then try git push. It is rejected. Run git pull origin main to merge their work in, then push again.

Try these on purpose. Commit before setting your name. Push before adding a remote. Let a teammate push, then try to push yourself. Each produces the same error you will meet on a real machine, and the fix.

06 Parallel universes

Branching & merging

Branching lets you diverge from the main line of development and keep working without disturbing it. A branch in Git is only a movable label pointing at a commit, which is why creating one is instant.

Merging takes independent lines of development and joins them into one branch. If the target has not moved, Git simply slides the label forward (a fast-forward). If both sides moved, Git creates a merge commit with two parents. On GitHub, a pull request wraps a merge in code review.

07 A team convention

The branching model: master, develop and supporting branches

The master branch at origin holds production code, and every commit on it is a release. Parallel to it runs develop, where finished work is integrated for the next release. Both live forever.

Around them sit supporting branches with a limited lifetime: feature, release and hotfix branches. Each has strict rules about where it starts and where it must be merged. Technically they are plain Git branches. The categories come from how the team uses them.

11 Landing

Key takeaways

01

Version control is a history, not a backup

Every commit records what changed, who changed it, when, and why. That record lets a team find a bug's origin and undo it safely.

02

Edit, stage, commit, push

Files move from the working directory to the staging area with git add, into your local repository with git commit, and to the remote with git push.

03

Branches are cheap, so use them

Do new work on its own branch, keep master releasable and develop integrated, and bring work back with a reviewed merge.
