01 · Why this exists

The problem it solves: “it works on my machine”

A trained model is more than a .pkl file. It depends on a Python version, library versions, system libraries and environment variables. Ship only the code and the server has to recreate all of that by hand, and it usually gets something slightly wrong.

02 · Virtualisation

Virtual machines vs containers

Both isolate workloads, at different levels. A VM virtualises hardware: a hypervisor runs a full guest OS, with its own kernel, for each app. A container virtualises the operating system: apps share the host's Linux kernel and are fenced off with kernel features (namespaces control what a process can see, cgroups control how much CPU and memory it may use).

Choose VMs when…

you need a different kernel or OS (Windows on Linux hardware), hard multi-tenant security boundaries, or you're running legacy systems. Cloud instances are themselves VMs.

Choose containers when…

you want fast, dense, reproducible deployments of Linux services, such as model APIs, batch jobs or pipelines. In practice you usually run containers inside VMs.

03 · Two tools, two jobs

Docker is not Kubernetes

Docker builds and runs containers on one machine. Kubernetes orchestrates containers across many machines: it decides where they run, restarts them when they die, scales them and routes traffic to them. They complement each other.

Image vs container

An image is a read-only, layered template (think: class / recipe). A container is a running instance of it with a thin writable layer on top (think: object / the dish). One image → many containers.

Kubernetes doesn't need Docker Engine

Kubernetes runs containers through a CRI runtime such as containerd or CRI-O; built-in Docker Engine support (dockershim) was removed in v1.24. Images you build with Docker still run unchanged, because both follow the OCI image standard.

Where the image lives

A registry stores and serves images: Docker Hub, GitHub Container Registry, AWS ECR, Google Artifact Registry, Azure ACR. Kubernetes nodes pull from it, so a cluster can only run images it can reach.

06 · Images under the hood

Dockerfile layers & the build cache

Each instruction in a Dockerfile makes a layer. Docker reuses (caches) a layer if that instruction and everything above it is unchanged. Once one layer changes, every layer below it is rebuilt. Order matters: put the slow, rarely changing steps first.

Lab · make the build fast
Dockerfile instruction order
Build history appears here. Build once, edit app.py, then build again in each order and compare the times.

Image hygiene for ML

Use slim base images (python:3.11-slim); add a .dockerignore so datasets, .git and notebooks don't enter the build context; pin package versions; use multi-stage builds to keep compilers out of the final image; never bake secrets into layers.

Models in or out of the image?

Small models can be COPY'd in, giving one immutable artifact per model version. Large models are often pulled at start-up from object storage or a model registry, or mounted as a volume, to keep images small.

12 · Wrap-up

Key takeaways

  1. Containers package the environment, not just the code. That is what makes ML deployments reproducible across laptop, CI and production.
  2. VMs virtualise hardware; containers virtualise the OS. Containers share the host kernel, so they are smaller and start in milliseconds, with weaker isolation than a VM.
  3. Image = template, container = running instance. Images are immutable and versioned by tag; containers are disposable.
  4. Order your Dockerfile for the cache. Dependencies first, code last, so a code change rebuilds in seconds.
  5. Containers are ephemeral; state lives in volumes (Docker) or PersistentVolumes (Kubernetes), or in an external store.
  6. Kubernetes is declarative. You state the desired state; controllers reconcile constantly, which is why deleted pods come back.
  7. Deployments give you rolling updates and instant rollback. A bad model image stalls the rollout instead of taking the service down.
  8. Services give pods a stable address. Pods come and go with new IPs; clients talk to the Service.

Glossary

Hypervisor
Software that runs virtual machines by virtualising hardware (KVM, ESXi, Hyper-V).
Namespaces
Linux kernel feature that limits what a process can see (its own PIDs, network, mounts, hostname).
cgroups
Linux kernel feature that limits what a process can use (CPU, memory, I/O).
Image
Read-only stack of filesystem layers plus metadata (entrypoint, env, ports).
Layer
The filesystem diff produced by one Dockerfile instruction; cached and shared between images.
Container
A running (or stopped) instance of an image with its own writable layer.
Registry
Server that stores and distributes images (Docker Hub, ECR, GAR, GHCR).
Tag
Human-readable label for an image version, such as iris-api:1.1. latest is just the default tag, not "newest".
Volume
Storage managed by Docker that outlives any single container.
Docker Compose
YAML file plus CLI to run a multi-container app on one host.
Node
A machine (VM or physical) in a Kubernetes cluster that runs pods.
Pod
One or more containers scheduled together, sharing network and storage.
Deployment
Declares desired replicas and pod template; manages rollouts via ReplicaSets.
Service
Stable network endpoint load-balancing to pods selected by labels (ClusterIP, NodePort, LoadBalancer).
kubelet
Agent on every node that makes sure the pods assigned to it are running.
etcd
Consistent key-value store holding the entire cluster state.
Reconciliation
The control loop: observe actual state, compare to desired, act to close the gap.
