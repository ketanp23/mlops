02 · Coverage

What to monitor: four layers

Classic monitoring covers the bottom layer. ML needs all four, because each catches failures the others can't see.

Layer 1 · system / service

Is it up and fast?

Latency (p50/p95/p99), throughput, error rate, saturation (CPU, memory, GPU, queue depth). The "golden signals". Tools: Prometheus, Grafana, Datadog, CloudWatch.

Layer 2 · data

Is the input what the model expects?

Schema violations, missing values, out-of-range values, new categories, and distribution shift between training and live data (data drift). Tools: Evidently, Great Expectations, WhyLabs, NannyML.

Layer 3 · model

Is it still right?

Prediction distribution and confidence, and, once ground-truth labels arrive, accuracy / F1 / calibration (concept drift shows up here). When labels are delayed, watch proxies such as prediction drift and confidence.

Layer 4 · business

Is it still useful?

The outcome the model exists for: approved loans that default, fraud caught, click-through, revenue per recommendation. This is where a "technically fine" model can still be failing.

03 · Data drift

Drift lab: reference vs production

Grey is the training (reference) distribution of petal_length; blue is this week's production data. Move the sliders or pick a preset, and watch the two most common drift statistics react.

reference (training, n=2,000)production (this week, n=2,000)

PSI

Population Stability Index: bins the reference into deciles and sums (cur − ref) × ln(cur / ref). Rules of thumb: < 0.1 stable, 0.1–0.25 moderate shift, > 0.25 significant.

KS test

Kolmogorov–Smirnov: largest gap between the two cumulative distributions, with a p-value. With thousands of rows, even tiny, harmless shifts become "significant", so read the size of D, not just p.

Drift ≠ bad model

Drift is a signal to look, not proof of failure. Confirm with performance once labels arrive, check which features matter most to the model, and fix upstream bugs before retraining on broken data.

04 · Logging

Logging predictions you can actually use

Logs are how you answer "why did the model say that, for whom, and which version?" weeks later. Build a prediction log line and see what each field buys you, or costs you.

Lab · design a prediction log

    Levels

    DEBUG for development, INFO for each prediction or request summary, WARNING for degraded-but-served (fallback model, slow), ERROR for failed requests. Alert on rates, not individual lines.

    Correlate

    Generate a request_id (or OpenTelemetry trace_id) at the edge and pass it through every service. One ID then finds the gateway, feature store and model logs for a single request.

    Cost & privacy

    Never log raw PII; hash or drop it. Sample high-volume INFO logs (e.g. 10%) but keep 100% of errors. Set retention by purpose: debug logs for days, prediction logs for drift/audit as long as policy allows.

    06 · Alerting

    SLOs, error budgets and alerts that matter

    An SLI is a measurement (share of requests answered OK in < 300 ms). An SLO is the target for it (99.9% over 30 days). The gap to 100% is your error budget. Alert when you're burning it too fast, not on every blip.

    Lab · error budget calculator

    Good alerts

    • Fire on symptoms users feel (errors, latency, bad predictions), not causes (CPU 80%).
    • Use a for: duration or multi-window burn rates to skip blips.
    • Every page links to a runbook with the first three things to check.
    • Ticket-level alerts (slow drift, budget trending down) go to a queue, not a pager.

    ML-specific alerts

    • PSI > 0.25 on a top-5 important feature for 1 day
    • Missing-value rate on any required feature > 5%
    • Prediction class mix shifts > 20% vs last 4 weeks
    • Labelled accuracy below SLO on the latest complete window
    • Model version in production ≠ version in the registry's @champion

    Common anti-patterns

    “Works in my notebook”

    Training only reproducible on one laptop. Fix: pipelines as code, pinned environments, versioned data.

    Train/serve skew

    Features recomputed differently in the API. Fix: one feature library or a feature store used by both paths, plus a parity test.

    Deploy and forget

    No model-level monitoring; issues found by customers. Fix: four-layer monitoring and owned alerts with runbooks.

    Retrain on a timer, blindly

    Auto-retrain on broken upstream data and ship it. Fix: data validation and champion/challenger gates before any automatic promotion.

    Untracked experiments

    “Which params made the good model?” Fix: log every run (MLflow / W&B), register what ships.

    Pager fatigue

    Alerts on every metric twitch get muted. Fix: SLO-based alerts, symptom-first, with severity levels.

    12 · Wrap-up

    Key takeaways

    1. Models degrade silently. Green system dashboards say nothing about whether predictions are still right.
    2. Monitor four layers: system, data, model and business. Each catches failures the others miss.
    3. Drift is a signal, not a verdict. PSI and KS tell you where to look; labels and business metrics tell you whether it matters.
    4. Log structured, correlated, privacy-safe events with model version, request ID, features and prediction for every request.
    5. Alert on symptoms and SLO burn rate, with a for: window and a runbook. Fewer, better alerts.
    6. Close the loop: drift or performance alerts trigger a gated retraining pipeline, and the result goes out by canary.
    7. Write recipes down. Rollback, reproduce, shadow-test and debug playbooks turn incidents into routine.
    8. Grow maturity step by step: reproducibility and tracking first, then pipelines and monitoring, then full CI/CD of the pipeline.

    Glossary

    Observability
    Being able to explain a system's behaviour from its outputs: metrics, logs and traces.
    Metric / log / trace
    Numbers over time (cheap, aggregated) / individual events (detailed) / a request's path across services.
    p95 latency
    95% of requests were faster than this. Tails matter more than averages.
    Data drift
    Change in the distribution of model inputs compared with training data.
    Concept drift
    Change in the relationship between inputs and the correct output.
    PSI
    Population Stability Index, a binned measure of distribution shift.
    KS statistic
    Maximum distance between two cumulative distributions.
    Ground truth delay
    Time until the true label is known (minutes for clicks, months for loan default).
    SLI / SLO / SLA
    What you measure / the target you set / the contractual promise to a customer.
    Error budget
    The amount of unreliability an SLO allows (1 − SLO) over a window.
    Burn rate
    How fast the error budget is being consumed relative to plan (1× = exactly on budget).
    Runbook
    Step-by-step instructions for responding to a specific alert.
    Feature store
    Shared system that computes and serves features consistently for training and serving.
    Continuous training
    Automatically retraining and validating a model when triggered by data, schedule or alerts.
