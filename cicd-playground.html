01 · Why this exists

The problem: release day, the manual way

A typical first ML deployment is a checklist in someone's head: pull the notebook, retrain, eyeball the accuracy, copy a pickle to a server, restart the service. Each step is a chance to ship the wrong thing, and nothing stops a bad model before users see it.

Lab · ten releases, two ways

🧑‍💻 Manual

  1. Pull latest notebook from someone's laptop
  2. Re-run training cells (in the right order?)
  3. Check accuracy by eye
  4. scp model.pkl to the server
  5. Update requirements.txt by memory
  6. Restart the service and hope

🤖 Pipeline

  1. Every change goes through a pull request
  2. CI runs lint, unit tests and data validation
  3. Training is a versioned, reproducible stage
  4. A quality gate compares against the current model
  5. The image is built once and promoted unchanged
  6. A canary release limits who sees a bad model
shipped fineproblem caught before usersincident in production
Pick a way to release…
CI/CD doesn't make people more careful. It turns the careful steps into code that runs on every change, in the same order, with gates that refuse to continue when something is wrong.

03 · Building MLOps pipelines

Anatomy of an ML pipeline

Each stage either produces an artifact or acts as a gate that refuses to let a bad change through. Break something, then run the pipeline and see where it stops. The earlier a problem is caught, the cheaper it is.

Lab · run the pipeline
Pipeline log appears here.

Make stages idempotent

Re-running a stage with the same inputs must give the same outputs. Pin seeds and package versions, and read data by version, not "latest". Tools like DVC skip stages whose inputs haven't changed.

Build once, promote many

Build the container image a single time and move that exact image from staging to production by its digest. Never rebuild for prod, or you are testing one thing and shipping another.

Gate on a comparison

"Accuracy ≥ 0.90" alone isn't enough. Also require the challenger to beat (or match) the current champion on the same evaluation data, and check latency and model size.

Before a model goes to production

  1. Code, data version and params are committed (git + DVC)
  2. Experiment and metrics are tracked; model is in the registry with a version
  3. Challenger beats champion on the same holdout set
  4. Latency, memory and image size are within budget
  5. Input schema is validated at the API boundary
  6. The image is scanned and referenced by digest
  7. Smoke tests pass in staging with production-like config
  8. Monitoring, dashboards and alerts exist for the new version
  9. The rollback path is tested, not assumed

11 · Wrap-up

Key takeaways

  1. CI checks every change; CD ships it. Continuous delivery stops at a human approval; continuous deployment doesn't.
  2. ML adds data and models to the pipeline. Version all three, and let new data, schedules or alerts trigger it, not only commits.
  3. Pipelines are stages plus gates. Tests, data validation and model quality gates stop bad changes as early (and cheaply) as possible.
  4. Reproducibility is a feature. DVC re-runs only what changed and can rebuild any past model from a commit.
  5. Track every run; promote from a registry. MLflow records params and metrics; aliases like champion decide what serves.
  6. Build the image once, promote it by digest. What you tested is exactly what you ship.
  7. Release progressively. Canary plus automated analysis means a bad model reaches a few users for a short time and rolls itself back.
  8. Practise rollback. Blue-green gives an instant switch back; make sure you've used it before you need it.

Glossary

Pipeline
An automated, ordered set of stages (build, test, train, deploy) triggered by an event.
Workflow / job / step
GitHub Actions terms: a workflow YAML has jobs; jobs run steps on a runner.
Quality gate
A check that must pass for the pipeline to continue (e.g. accuracy ≥ champion).
DVC
Data Version Control: versions data and models alongside git and runs pipelines defined in dvc.yaml.
dvc.lock
Records the exact hashes of every stage's inputs and outputs, so a pipeline run can be reproduced.
Experiment tracking
Recording each training run's code version, params, metrics and artifacts (e.g. MLflow).
Model registry
A catalogue of model versions with metadata and aliases such as champion / challenger.
Champion / challenger
The model currently serving vs a candidate that must beat it to replace it.
Canary
Sending a small share of traffic to the new version first and widening it if metrics stay healthy.
Blue-green
Running the new version (green) alongside the old (blue) and switching all traffic at once.
Shadow deployment
Mirroring live traffic to a new model whose responses are logged but never returned.
AnalysisRun
Argo Rollouts object that queries metrics (e.g. Prometheus) during a rollout and fails it if thresholds are breached.
GitOps
The cluster's desired state lives in git; a controller (Argo CD, Flux) syncs it.
Image digest
An immutable content hash (sha256:…) identifying one exact image, unlike a movable tag.
